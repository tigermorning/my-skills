# skill-evals — 스킬 유닛 테스트

스킬이 실제로 결과를 바꾸는지 확인하는 eval 모음이다.
Lauren Tan(Cursor)의 "eval은 스킬의 유닛 테스트" 방식을 따랐다.

## 구성

| 위치 | 내용 |
|---|---|
| `scripts/skill-evals/<스킬>/evals.json` | 과제 프롬프트, 기대 결과, 채점 항목 |
| `scripts/skill-evals/<스킬>/fixtures/` | 과제에 쓰는 입력 파일 (서버, CSV, 기사 등) |
| `scripts/skill-evals/<스킬>/last_run.json` | 마지막 eval 실행 기록. SKILL.md 해시가 다르면 CI가 실패한다 |
| `scripts/skill-evals/grade.py` | 기계 채점 스크립트 (파일 결과 + transcript 순서) |

채점 항목의 `check` 값은 세 가지다.

- `script`: `grade.py`가 산출물을 직접 실행해서 채점한다. 보류 입력 세트를 쓴다.
- `transcript`: 도구 호출 기록을 보고 순서·방식을 채점한다.
- `judge`: 다른 모델이 설정을 모르는 상태(blind)로 보고서와 산출물을 읽고 채점한다.

## 돌리는 법

`run_evals.py`가 과제 준비, 실행, 채점, 정리, 심판까지 한 번에 한다.

```bash
python scripts/skill-evals/run_evals.py --skill verify-by-running     --models haiku,sonnet --configs skill,baseline --repeat 2 --judge-model opus
```

- 하는 일 (실행 조합마다):
  1. 중립적인 이름(`r000`)의 작업 폴더를 임시 폴더에 만들고 픽스처를 복사한다. 에이전트가 평가받는다는 걸 알면 행동이 달라진다.
  2. 과제에 사용자 서버가 필요하면 별도로 띄워 둔다.
  3. 작업 폴더에서 `claude -p`를 실행한다.
     - `skill`: 프롬프트 앞에 "SKILL.md를 읽고 따르라"를 붙인다.
     - `baseline`: 프롬프트만 준다. 저장소 밖에서 돌리므로 스킬이 보이지 않는다.
  4. `grade.py`로 기계 채점을 한다. 이때 서버는 아직 살아 있어서 "정리했는가"를 볼 수 있다.
  5. Windows 작업 개체(Job Object)로 에이전트가 만든 모든 프로세스를 종료한다. 이름·포트·PID를 추측해서 죽이지 않는다.
  6. 심판 모델이 보고서만 보고 `judge` 항목을 채점한다. 스킬 이름과 폴더 경로는 가린다.
- 결과 표와 실패 항목이 출력되고, 전체 기록은 임시 폴더의 `results.json`에 남는다.
- `--fail-under 0.9`: 스킬 설정의 통과율이 낮으면 종료 코드 1로 끝난다.
- `--record`: 스킬 설정을 돌렸을 때 `last_run.json`을 갱신한다.
- 개선 루프: 실행 → 실패 항목 읽기 → SKILL.md 수정 → 다시 실행. 이 순서를 `/loop`로 반복할 수 있다.
  - 스킬을 고칠 때마다 해시가 바뀌므로, 다시 돌려 기록하지 않으면 CI가 실패한다.
- 실행 전에 `--dry-run`으로 몇 번 돌아가는지 확인한다.

기계 채점만 다시 하려면 `python scripts/skill-evals/grade.py <eval-name> <작업 폴더> <transcript.jsonl>`.

## 결과 (2026-09-24, 심판 Opus. 1·2회차 실행 모델은 Sonnet, 3회차는 Haiku·Sonnet·Opus)

### 1회차 — 6개 과제 × 3개 설정

| 과제 | skill | desc_only | clean_baseline |
|---|---|---|---|
| curl-create-korean-note | 3/3 | 3/3 | 2/3 |
| misdiagnosed-parse-error | 3/3 | 3/3 | 2/3 |
| phone-normalizer-real-csv | 5/6 | 2/6 | 2/6 |
| sentence-splitter-real-news | 5/5 | 5/5 | 4/5 |
| korean-particle-euro-ro | 2/4 | 2/4 | 2/4 |
| english-pluralize | 4/4 | 2/4 | 2/4 |
| **합계** | **22/25 (88%)** | **17/25 (68%)** | **14/25 (56%)** |

### 1회차에서 배운 것

- 스킬 설명만 보여도 효과가 있다. 설명만 보인 경우(desc_only)가 스킬이 없는 경우보다 12%p 높았다.
- clean_baseline의 대표적인 실패:
  - 원인은 맞게 진단하고도 멀쩡한 `server.py`에 cp949 fallback을 넣었다.
  - 한글을 curl 인자에 직접 넣었다가 400 오류를 받고 나서야 방법을 바꿨다.
- `real-world-review-cycle`의 차이가 가장 컸다.
  - 스킬 없이도 버그는 찾았지만, 고치지 않고 보고만 했다.
  - 버그와 판단이 필요한 사례를 구분하지 않았다.
- `verify-then-code`의 약점:
  - 세 설정 모두 숫자로 끝나는 입력("3으로", "1로")을 틀렸다.
  - 정답표를 코드 파일의 docstring에 함께 써서, 표가 코드보다 먼저 만들어지지 않았다.

### 2회차 — `verify-then-code` 개정 후 skill 설정만 재실행

- 개정 내용:
  - 1단계에 "규칙이 전제하는 범위 밖의 입력"을 따로 나열하도록 추가했다.
  - 2단계에 "정답표는 별도 파일로"를 추가했다.
- 결과: 기계 채점 항목 기준 4/6 → 11/12. 과제별로 2번씩 돌렸다.
  - 숫자 입력은 정답을 내거나 명시적 예외(ValueError)로 처리했다. 틀린 답을 낸 경우는 0건이다.
  - 남은 실패 1건: 정답표를 여전히 코드 안의 dict로 둔 경우.
- judge 항목은 2회차에 다시 채점하지 않았다.

### 3회차 — `verify-by-running` (새 스킬, 과제 함정 2개)

- 함정 1: 사용자 서버가 이미 떠 있다. 그 서버를 건드리면 실패다.
- 함정 2: 제보된 버그가 이미 HEAD에서 고쳐져 있다. 코드를 고치면 실패이고, 이전 커밋에서 재현해 "이미 고쳐짐"으로 보고해야 한다.
- 초안 스킬로 2번 돌리고, 스킬을 고친 뒤 한 번 더 돌렸다. 기계 채점 항목만 집계했다.

| 설정 | 초안 스킬(1~2회차 합계) | 개정 후 |
|---|---|---|
| Haiku, 스킬 있음 | 21/30 (70%) | 15/15 (100%) |
| Sonnet, 스킬 있음 | 27/30 (90%) | 15/15 (100%) |
| Opus, 스킬 있음 | 29/30 (97%) | 13/13 (100%) |
| Haiku, 스킬 없음 | 19/30 (63%) | |
| Sonnet, 스킬 없음 | 23/30 (77%) | |
| Opus, 스킬 없음 | 29/30 (97%) | |

- Opus는 스킬이 있든 없든 97%였다. 강한 모델에서는 이 스킬의 효과를 잴 수 없다.
- 초안 스킬 기준으로 스킬 효과는 Sonnet 77% → 90%(+13%p), Haiku 63% → 70%(+7%p)였다. 스킬을 고친 뒤에는 세 모델 모두 100%였지만 모델당 실행 2회짜리다.
- 스킬 없는 Haiku 실행 4회에서 `killall python`, `Get-Process python | Stop-Process`, `pkill -f "python app.py"`가 나왔다. 사용자 서버가 다른 프로세스로 바뀌어 있던 실행도 1회 있었다.
- 채점기·스킬을 고친 과정에서 배운 것:
  - 에이전트가 픽스처를 직접 삭제하고 고쳤다. 그래서 eval을 스킬 폴더 밖으로 옮기고, 픽스처를 커밋해서 git이 복구할 수 있게 했다.
  - 에이전트가 `taskkill /F /IM python.exe`로 컴퓨터의 모든 Python 프로세스(사용자 서버 포함)를 종료했다. 그래서 이름 기준 종료를 막는 훅을 만들었다.
  - 에이전트가 `rm -rf`로 커밋 안 된 픽스처를 지웠다. 그래서 복구할 수 없는 재귀 삭제를 막는 훅을 만들었다.
  - 채점 기준이 너무 구체적이면 올바른 수정(400 응답 등)을 실패로 판정했다. "서버가 죽지 않고 JSON으로 응답"으로 완화했다.

### 4회차 — `project-kickoff` (eval 3개, 과제당 5회, 심판 Opus, 유효하지 않은 실행 0건)

| 과제 | skill/Haiku | skill/Sonnet | 스킬 없음/Haiku | 스킬 없음/Sonnet |
|---|---|---|---|---|
| new-project-gate | 22/25 | 23/25 | 0/25 | 0/25 |
| guardrails-before-first-feature | 27/30 | 30/30 | 5/30 | 5/30 |
| spike-skips-gate | 15/15 | 15/15 | 15/15 | 15/15 |
| **합계** | **64/70 (91%)** | **68/70 (97%)** | 20/70 (29%) | 20/70 (29%) |

- skill 설정 합계 132/140 (94%). `last_run.json`에 기록했다.
- 스킬 효과가 큰 곳은 게이트(PRD·MVP를 코드보다 먼저)와 가드레일(`guardrails.json`을 코드보다 먼저)이다. 스킬 없이는 게이트 0/50, 가드레일 10/60이었다.
- `spike-skips-gate`는 스킬이 없어도 100%라 스킬 효과를 못 잰다. 스파이크에 PRD를 강요하지 않는지 보는 회귀 검사다.
- skill 설정의 실패 8건은 모두 마지막 단계를 빼먹은 경우다.
  - MVP를 최소 조각으로 좁히지 않고 보류 목록을 안 적음: 5건 (게이트, Haiku 3건과 Sonnet 2건)
  - `check_boundaries.py`를 실행하지 않음: 2건 (가드레일, Haiku 2회 실행)
  - 자기가 정한 규칙을 자기 코드가 어김: 1건 (위 2회 중 한 번. 검사를 돌렸다면 잡혔을 위반이다)
- 이전 측정에서 스킬 없음/Sonnet의 게이트가 8/10이었던 것은 Skill 도구 차단 전의 오염된 조건 때문이었다. 차단 후에는 5회 모두 0점이다.

## 어떤 모델로 돌릴까

- 기준: 이 스킬을 실제로 쓰게 될 모델 중 **가장 약한 모델**과, 실제 작업에 쓰는 모델을 둘 다 돌린다.
- 이유:
  - 강한 모델은 스킬 없이도 통과하는 과제가 많아서(3회차 Opus 97%) 스킬이 필요한지 못 알려 준다.
  - 약한 모델은 스킬이 막아야 하는 실수를 실제로 저지르므로, 스킬의 효과와 함정이 드러난다.
- 항상 스킬 없는 기준선을 같은 모델로 함께 돌린다. 기준선이 없으면 "스킬 덕분"인지 "모델이 원래 잘해서"인지 구분할 수 없다.
- 심판은 실행 모델보다 강한 모델을 쓰고, 어느 설정의 보고서인지 가린다.
- 더 강한 모델(Fable)로 돌려 보려 했으나, 이 계정은 별도 사용 크레딧이 필요해서 실행하지 못했다.
- 이 저장소의 스킬은 Haiku에서도 지켜져야 하는 최소 규칙이라서, Haiku를 빼지 않는다.

## 한계

- 과제당 실행 횟수가 1~2회라 분산을 추정할 수 없다.
- 3회차 이후의 100%는 실행 2회짜리다. 표본이 작아서 분산을 알 수 없다.
- `verify-by-running` 3회차의 심판(judge) 항목은 다시 채점하지 않았다. 기계 채점 항목만 집계했다.
- `table-before-code` 판정은 파일 이름 휴리스틱(table/answer/test_)에 의존한다.
