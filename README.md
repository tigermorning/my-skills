# my-skills

내가 AI 코딩 도구에게 반복해서 시키던 일을 재사용 가능한 스킬로 만들어 모아두는 저장소입니다.
여기 있는 스킬은 **어느 프로젝트에서나 그대로 쓸 수 있는 범용 스킬**만 다룹니다.
프로젝트에 강하게 종속된 스킬은 이 저장소에 두지 않고, 각 프로젝트 안에 남겨둔 뒤
아래 "프로젝트 전용 스킬 카탈로그"에서 위치만 기록합니다 (필요할 때 찾아서 참고 또는 변형).

스킬 말고 **항상 적용되는 행동 규칙**(예: PR 생성 전 확인)은 `CLAUDE.md`에
따로 모아둡니다. 스킬은 특정 작업 유형에 매칭될 때만 발동하는 절차이고,
규칙은 어떤 작업이든 매번 적용되는 기본값이라 성격이 달라 구분합니다. 다른
프로젝트에 적용하고 싶으면 그 프로젝트의 `CLAUDE.md`에 해당 항목을 그대로
복사해 넣으면 됩니다.

## 설치 (사용자 전역 설치가 기본)

- 스킬은 `~/.claude/skills/<스킬명>/SKILL.md` 위치에 있어야 모든 프로젝트에서 인식됩니다.
- `~/.claude/skills/omc-learned/<스킬명>/`처럼 한 단계 더 들어가면 인식되지 않습니다.
  - 중립 폴더에서 Skill 도구로 호출해 `Unknown skill`이 나오는 것을 확인했습니다.
- 이 저장소의 스킬은 사용자 전역 위치에 설치해 두었고, 저장소를 고치면 같은 위치에 다시 복사합니다.
- 전역 사본이 저장소와 어긋났는지 확인하고 맞추는 명령:
  - 확인: `python scripts/installed_skills.py`
  - 맞추기: `python scripts/installed_skills.py --sync`
  - `python scripts/check_skills.py`도 로컬에서 같은 검사를 하고, 어긋나면 실패합니다. CI에서는 건너뜁니다.

다른 컴퓨터에 새로 세팅하거나, 특정 프로젝트에만 국한해서 쓰고 싶다면:

```bash
# 사용자 전역 (모든 프로젝트에 자동 적용)
cp -r .claude/skills/<스킬명> ~/.claude/skills/<스킬명>

# 또는 프로젝트 한정
cp -r .claude/skills/<스킬명> /path/to/project/.claude/skills/<스킬명>
```

Claude Code가 아닌 다른 도구를 쓴다면, 그 도구의 스킬/커스텀 명령 위치
(예: Cursor의 `.cursor/rules`, 그 외 도구의 커스텀 프롬프트 폴더)에
`SKILL.md`의 frontmatter를 뺀 본문 내용을 붙여 넣으면 동일하게 동작합니다.

## 범용 스킬 카탈로그

### non-ascii-via-file — 한글을 명령어에 직접 넣지 않기

Windows Git Bash 등에서 터미널 명령어(curl, git commit -m, python -c 등)에 한글을
직접 넣으면 실제 프로그램에 전달되기 전에 인코딩이 깨집니다. 이게 겉으로는 진짜
버그처럼 보여서("요청 형식이 잘못됐다") 멀쩡한 코드를 의심하며 시간을 낭비하기
쉽습니다. 이 스킬은 비ASCII 텍스트를 파일에 먼저 써두고 명령어가 그 파일을
참조하게 만듭니다. 서버가 있는 프로젝트에 국한되지 않고, 한글이 포함된 값을 셸
명령어로 넘기는 모든 상황에 적용됩니다.
(2026-09-24 재현: 이 환경에서 깨지는 건 `curl -d`였고, `git commit -m`·`python` 인자는
정상이었습니다. curl 쪽은 아래 "하드 가드"의 훅이 기계적으로 막습니다.)

### verify-then-code — 예외 있는 규칙은 코드보다 정답표 먼저

`korean-subtitle-corrector`에서 "규칙이 이럴 것"이라는 가정으로 문법 로직을 먼저
코딩했다가 같은 오교정 실수를 두 번 반복한 뒤 확립된 절차를 일반화했습니다.
예외가 있을 수 있는 규칙(문법, 세금/법률 조건, 데이터 분류 기준 등)을 다룰 때,
권위 있는 근거로 "입력 → 정답" 표부터 만들고 코드가 그 표를 따라가게 합니다.
문법 교정기뿐 아니라 권위 있는 근거가 존재하는 모든 규칙 기반 도메인에 적용됩니다.

### real-world-review-cycle — 코드 리딩이 아니라 실사용 검증

파서·교정기·분류기·생성기처럼 입력 공간이 넓은 로직은 코드를 아무리 꼼꼼히
읽어도 실제 입력에서만 드러나는 버그를 놓치기 쉽습니다. 실사용 데이터로 돌려서
사람이 직접 대조하고, 확실한 버그는 즉시 근본 원인을 고치고, 판단이 필요한
애매한 사례는 코드를 건드리지 않고 플래그만 남기는 반복 절차입니다.

### decision-log — 확인된 사실은 기록, 답하기 전엔 조회부터

같은 대화·프로젝트에서 "된다/안 된다"를 뒤집거나, 이전에 확인한 내용을
기억 못 해 다시 헤매는 문제를 반복적으로 겪은 뒤 만들었습니다. 확인
가능한 근거를 조회하지 않고 기억/추측으로 답하는 게 원인이라서, 프로젝트별
결정 기록을 먼저 확인하고 없으면 직접 검증한 뒤 즉시 기록하는 절차를
강제합니다. `verify-then-code`의 원칙을 도메인 규칙이 아니라 AI 자신의
답변 일관성에 적용한 버전입니다.

### spec-freshness-check — 세션 시작 시 외부 근거가 개정됐는지 확인

법령·공식 규정·서드파티 API 버전처럼 프로젝트 코드와 무관하게 바뀔 수
있는 외부 근거에 의존할 때, 마지막 확인 이후 바뀐 게 있는지 세션 시작
시점에 확인합니다. `korean-subtitle-corrector`의 프로젝트 전용 스킬
`session-start-regulation-check`(국립국어원 어문 규정 확인용)를 일반화한
것입니다.

### external-search-cache-proxy — 쿼터 있는 외부 검색 API는 캐시+검증 프록시로

`Fridge2Plate`(포크해서 참고 중인 프로젝트)의 YouTube Data API 연동 코드를
읽고 일반화했습니다. 쿼터·비용이 있는 외부 검색/조회 API(YouTube, Google
Maps, OpenAI 등)를 통합할 때, 클라이언트가 직접 부르지 않게 서버 라우트로
감싸고, 캐시 테이블을 먼저 확인하고, 반환된 식별자를 iframe src나 다음
쿼리에 쓰기 전에 형식 정규식으로 검증합니다. (참고: 이 스킬은 직접 겪은
실수가 아니라 남의 코드를 읽고 배운 패턴이라, 실전에서 검증되면서 계속
다듬어질 여지가 있습니다.)

### frontend-design — 템플릿처럼 보이지 않는 UI 디자인 (Anthropic 공식 참고자료)

Anthropic 공식 `frontend-design` 플러그인 스킬 원문을 그대로 가져왔습니다. 직접 겪은
교훈은 아니고, 새 UI를 만들거나 기존 UI를 다시 디자인할 때 톤/타이포그래피/레이아웃을
"AI가 만든 티 나는 기본값"에서 벗어나게 잡아주는 참고 가이드입니다.

### project-session-memory — 프로젝트별 세션 간 기억 자동화

세션을 헷갈려서 새로 열거나 대화가 여러 세션으로 나뉠 때마다 맥락을 다시
설명해야 하는 문제를 훅으로 해결합니다. 다른 스킬들과 달리 SKILL.md
지침만이 아니라 실제 훅 스크립트(`scripts/session-memory-end.sh`,
`scripts/session-memory-start.sh`)를 함께 담고 있어서, 적용하려는
프로젝트의 `.claude/hooks/`와 `.claude/settings.json`에 실제로 설치해야
작동합니다. `Stop` 훅은 매 턴마다 발동해서 부적합하다는 것을 확인한 뒤,
세션 종료 시 원본만 빠르게 캡처해서 로컬 `git commit`까지 하는
`SessionEnd`(push는 안 함 — Claude Code auto-mode 분류기가 세션마다
무인으로 push하는 훅 설치를 막음)와, 다음 세션 시작 시 그 캡처를 다시
컨텍스트로 얹어주는 `SessionStart`의 조합으로 설계했습니다. 한때 같은
목적의 `durable-session-log`(수동 기록 방식)가 따로 있었지만, 두 스킬을
유지할지 하나로 합칠지가 여러 세션에 걸쳐 계속 뒤집히는 소모전이 된 끝에
이 스킬 하나로 최종 통합했습니다 — 자세한 배경은 이 스킬의 SKILL.md
참고.

### project-kickoff — PRD·MVP 없이는 코드부터 짜지 않기

새 프로젝트를 시작할 때(또는 기존 프로젝트의 방향을 크게 다시 잡을 때) PRD와
MVP 범위 정의를 다른 모든 작업보다 먼저 게이트로 두고, 그 다음부터는
project-session-memory, 의미 있는 단위마다 PR, README 최신화, 시크릿 관리,
PRD 성공 기준에 묶인 완료 정의를 프로젝트 내내 유지하는 체크리스트입니다.
이미 PRD/MVP가 확정된 프로젝트에 기능을 하나 더 얹는 상황에는 게이트를
다시 요구하지 않고, 예/아니오 하나만 확인하면 끝나는 1회성 기술 스파이크·
PoC에는 게이트를 아예 적용하지 않습니다(실제 프로젝트 4곳에 대조해보고
확인한 예외).

에이전트가 코드를 쓰는 프로젝트에는 첫 기능 전에 하드 가드레일(구조 규칙, CI가 막는 금지 패턴,
리뷰 코멘트를 검사로 승격)을 겁니다. 번들된 `check_boundaries.py`가 규칙마다 "대신 무엇을 쓸지"를
요구하는 경계 검사를 제공합니다.

### verify-by-running — 읽지 말고 돌려서 증명하기

"고쳤다", "된다"고 말하기 전에 사용자가 닿는 방식 그대로 실제로 실행해서 확인하게 합니다.
버그 제보가 오면 고치기 전에 현재 코드에서 재현부터 하고, 재현이 안 되면 이전 커밋을 별도
worktree로 띄워 "이미 고쳐졌는지"를 봅니다. 사용자가 이미 띄워 둔 서버는 건드리지 않고, 자기
포트로 따로 띄워 확인한 뒤 자기가 띄운 PID만 종료합니다. 결과는 관찰한 것과 건너뛴 것을 구분한
증거 형식으로 보고합니다. 번들된 `preflight.py`가 포트·git 상태·버전을 읽기 전용으로 점검합니다.

### feature-map — 에이전트가 기능까지 찾아가는 지도

UI가 있는 프로젝트에 `FEATURE_MAP.md`를 만들어, 에이전트가 앱을 띄우고 각 기능까지
스스로 찾아가 검증하게 합니다. 기능마다 적는 항목은 다음과 같습니다.

- 사용자 경로
- 단축키
- 선택자
- 파일
- 검증 방법

이 표 외에 맵은 `실행 방법`, `시작 전제조건`, `조작 관례`, `증거와 건너뜀 보고` 섹션을 갖습니다.
내부 구현은 적지 않고 사용자 관점으로 쓰는 법만 적습니다.

번들 체커(`scripts/check_feature_map.py`)는 다음을 검사합니다.

- 적힌 파일과 `path::Symbol`이 존재하는지
- 선택자가 화면에서 찾을 수 있는 것인지 (코드 식별자는 거부)
- 줄 번호나 보이지 않는 문자가 없는지
- 필수 섹션이 있는지

문장으로 적은 사실이 맞는지는 체커가 못 봅니다. 그래서 작성자가 아닌 에이전트가 무작위 표본을
코드와 대조하도록 스킬에 절차로 넣었습니다.
Lauren Tan(Cursor)이 검증 스킬의 핵심 부품으로 소개한 "피처 맵"을 일반화했습니다.

### worker-merge-gate — 일꾼 브랜치를 합칠 때 git 훅이 막는 관문

일꾼(에이전트)이 카드 하나씩 자기 브랜치에서 만들고 오케스트레이터가 합치는 저장소에 깝니다.
일꾼 브랜치를 지키는 브랜치에 합칠 때 훅이 다음을 판정하고, 하나라도 어기면 merge 커밋을 만들지 않습니다.

- 카드의 "만지는 파일" 밖을 고쳤으면 보고서에 적었는가 (금지 파일·프로젝트 밖은 지정 칸에 경로까지)
- 보고서의 필수 칸이 다 있고, 확인 칸에 실제 숫자가 있는가
- 빠른 검사(몇 분짜리)가 통과하는가

판정기는 합친 작업 트리가 아니라 HEAD 판으로 돌아서, 일꾼이 판정기를 고쳐 자기를 통과시킬 수 없습니다.
squash처럼 들어온 브랜치를 알 수 없는 합치기는 막고, fast-forward는 `--no-ff` 기본으로 막습니다.

- 번들: `scope_check.py`(범위·보고서 판정, `--retro`로 지난 합치기 되짚기) · `merge_gate.py`(`--install`·`--status`·훅) · 설정 틀
- 셀프 테스트 `test_merge_gate.py`: 임시 저장소에서 막혀야 할 경로(이름으로 숨기기, pull, squash, 판정기·카드 고치기, 충돌 커밋, fast-forward 등)와 통과해야 할 경로를 확인합니다.
- 따로 띄운 리뷰어가 첫 판의 우회 경로를 실제 git으로 재현했고, 모두 고친 뒤 셀프 테스트에 넣었습니다.
- 실제 프로젝트 둘에 옮겨 보니 문서 쓰는 버릇이 달라 새 오탐이 나왔습니다. 그래서 설치 전에 되짚기로 보정하는 단계를 절차에 넣었습니다.

### PR 병목 3종 — standards-review · pr-merge-danger · review-retro

Matt Pocock의 강연 "Fixing the PR Bottleneck"(AI Engineer Paris 2026)을 정리하며 일반화했습니다.
에이전트가 PR을 쏟아낼 때 사람 리뷰를 빠르게 하는 방법은 "빨리 읽기"가 아니라 사람 앞에 거르는 층을 쌓는 것이라는 주장입니다.

- `standards-review`: 코딩 규칙을 구현 에이전트 프롬프트가 아니라 별도 컨텍스트의 리뷰 에이전트가 집행합니다.
  - 규칙은 `CODING_STANDARDS.md`에 두고, 판단이 필요한 것만 적습니다. 기계로 잡을 수 있는 건 검사로 만듭니다.
  - 거짓 테스트(되받아쓰기, 소스 텍스트 검사, 실패할 수 없는 mock)를 잡습니다.
  - 기본 동작은 댓글이 아니라 고쳐서 커밋입니다.
- `pr-merge-danger`: PR 본문을 Summary(가장 작은 그림) → Evidence(돌려 본 결과) → Merge Danger(Door / Reason / Blast radius)로 씁니다.
  - one-way door만 사람이 끝까지 읽습니다.
  - 번들 `check_pr_body.py`가 빠진 절·채우지 않은 틀(`<…>` 칸, HTML 주석)과 diff의 one-way 신호를 잡습니다.
  - 신호는 diff의 바뀐 줄(`+`/`-`)과 머리 줄의 경로에서만 찾고, 문서 파일은 뺍니다. 신호가 없다고 two-way라는 뜻은 아닙니다.
  - 따로 띄운 리뷰어가 첫 판의 구멍을 재현했습니다: 틀을 그대로 내도 통과, 소제목·코드 블록에서 절이 끊김, UTF-16 diff를 조용히 통과, 문맥 줄·문서의 단어로 오탐. 모두 고치고 셀프 테스트에 넣었습니다.
  - 검사기 핵심을 하나씩 망가뜨린 사본 11개에서 셀프 테스트가 모두 실패하는 것을 확인했습니다.
  - 일꾼 보고서 틀과 절 이름이 달라 `worker-merge-gate`의 빠른 검사에 바로 걸 수는 없습니다(SKILL.md에 손으로 돌리는 법).
- `review-retro`: 같은 지적을 두 번 쓰지 않게, 사람의 지적을 모아 검사·규칙·포인터·삭제 후보로 바꿉니다.
  - 번들 `collect_feedback.py`가 gh PR 리뷰와 Claude Code 세션 기록에서 사람이 쓴 말을 모으고, 비슷한 말을 "다른 PR·세션에 걸친 반복"과 "같은 세션 안의 반복"으로 묶습니다.
  - 실제 세션 기록에 돌려 보니 오탐이 나왔고 고쳤습니다: 이어받은 세션의 복사본(uuid로 제거), 중단 표시, 예약 작업의 자동 프롬프트.
  - 리뷰어가 찾은 구멍도 고쳤습니다: 시스템 알림 블록이 붙은 사람 메시지를 통째로 버림(이제 `origin.kind`와 블록 단위로 판정), 압축 요약을 사람 말로 셈, 6000개에서 1분 넘게 걸리던 비교(이제 2초 안), 봇 댓글.
  - 단어 겹침이라 표현이 다른 같은 지적은 못 묶습니다. 결과는 판단할 후보 목록입니다.
- **규칙은 두 층**입니다. 프로젝트마다 다 따로 만들지 않습니다.
  - 사용자 공통: `$REVIEW_STANDARDS` → `~/.claude/REVIEW_STANDARDS.md` → `~/.claude/references/review-standards.md` 가운데 먼저 찾은 파일 하나. 어디서나 반복되는 판단 규칙과 "나에게 위험한 변경" 목록을 둡니다.
  - 프로젝트: 저장소 `CODING_STANDARDS.md`. 그 저장소에서 같은 지적이 두 번 나왔을 때만 만듭니다. 프로젝트 규칙이 이깁니다.
  - `check_pr_body.py`가 공통 파일의 ```` ```one-way ```` 블록(이름 | 저장소 | path·content | 정규식 | 막기)을 신호로 더합니다. 저장소 이름으로 좁힐 수 있어서, 예를 들어 비공개 자료 이름이 공개 저장소 README에 들어가면 막고, 블로그 글 경로는 블로그 저장소에서만 봅니다.
  - `collect_feedback.py`는 세션 폴더를 여러 개 받아 반복 묶음마다 `[shared by N projects]`/`[project X]`를 붙입니다. 옮길 층을 고르는 근거입니다. Claude Code worktree 폴더(`…--claude-worktrees-…`)는 같은 프로젝트로 셉니다.
  - 실제 데이터로 돌려 잡은 것: 규칙 줄 끝의 빈 칸 ` |`가 정규식에 붙어 모든 경로에 걸리던 것(이제 칸 나누기를 고치고, 빈 문자열에 맞는 정규식은 종료 코드 2), worktree 폴더를 다른 프로젝트로 세어 생긴 가짜 "공통" 묶음.

### pr-pipeline — 사람은 판정이 보낸 PR만 본다

위 세 스킬은 손으로 부르는 부품이라, 그것만으로는 사람 리뷰가 줄지 않았습니다. 이 스킬이 부품을 매번 같은 순서로 돌리고 마지막에 머지 판정을 냅니다.

- 순서: 검사 → `claude -p` 리뷰 에이전트(확실한 것은 고쳐서 커밋, 나머지는 질문, PR 본문 작성) → 검사 다시(깨지면 리뷰 커밋 revert) → `check_pr_body.py` → push·PR·CI → 판정.
- 자동 머지 조건(전부): 검사·CI 초록, two-way, 위험 신호 없음(기본 + 사용자 공통), 리뷰 질문 0, 변경 줄 수 상한 이하, 보호 경로 안 건드림. 하나라도 어긋나면 PR은 열린 채 이유가 댓글로 남습니다.
- 저장소마다 `.claude/pr-pipeline.json`. `auto_merge`는 기본 꺼짐 — 꺼져 있으면 "조건 충족"까지만 적고 사람이 머지합니다. 이 저장소도 지금은 판정만 합니다.
- 리뷰 에이전트는 push·reset·rebase·checkout·웹을 쓸 수 없고, 원래 바뀐 파일 밖을 고치면 질문으로 바뀝니다.
- 셀프 테스트 `test_pr_pipeline.py`: 가짜 원격 저장소·가짜 `claude`·가짜 `gh`로 판정 경로 19가지. 핵심 판정을 하나씩 망가뜨린 사본에서 실패하는지도 확인합니다.

## 하드 가드 (스킬·규칙을 기계적 강제로 바꾼 것)

스킬과 CLAUDE.md 규칙은 에이전트가 잊을 수 있는 "소프트" 강제입니다.
반복해서 지적한 규칙은 아래처럼 훅과 CI로 옮겨 두었습니다.

| 가드 | 종류 | 막는 것 | 위치 |
|---|---|---|---|
| curl 한글 인자 | PreToolUse 훅 (Bash·PowerShell) | `curl -d '한글'`처럼 비ASCII가 든 curl 호출 | `scripts/hooks/guard_curl_non_ascii.py` |
| 고정 GitHub URL | PreToolUse 훅 (브라우저 입력 도구) | `/tree/`·`/blob/`·`/commit/`·`/releases/tag/` URL 입력 | `scripts/hooks/guard_pinned_github_url.py` |
| 이름 기준 프로세스 종료 | PreToolUse 훅 (Bash·PowerShell) | `taskkill /IM`, `pkill`, `killall`, `Stop-Process -Name`처럼 같은 이름의 모든 프로세스를 죽이는 명령 | `scripts/hooks/guard_mass_kill.py` |
| 복구할 수 없는 재귀 삭제 | PreToolUse 훅 (Bash·PowerShell) | 임시 폴더 밖에서 커밋 안 된 파일이나 git 밖 파일이 든 폴더의 `rm -rf` | `scripts/hooks/guard_recursive_delete.py` |
| Bash 역슬래시 두 개 | PreToolUse 훅 (Bash) | 역슬래시 두 개(`\\`)가 든 Bash 명령 — 이 환경의 Bash 도구는 셸에 넘기기 전에 `\\`를 `\` 하나로 줄인다(작은따옴표·`<<'EOF'` 안도). 파이썬·JS 스크립트의 `\\r`가 진짜 CR이 되거나 정규식이 깨진다. Write 도구로 파일을 쓰고 실행하게 안내 | `scripts/hooks/guard_bash_double_backslash.py` |
| 스킬 구조 검사 | GitHub Actions `skills-ci` | 이름과 폴더 불일치, 깨진 `[[링크]]`, 잘못된 evals.json, 원본 픽스처를 통과시키는 채점기, eval을 다시 안 돌린 SKILL.md 수정, 날짜·경위가 적힌 코드 주석, 스크립트 셀프 테스트 실패 | `scripts/check_skills.py` |

- 훅 등록 위치: `~/.claude/settings.json`의 `hooks.PreToolUse`. 모든 프로젝트에 적용됩니다.
- 다른 컴퓨터에서는 같은 항목을 추가하고 경로만 바꾸면 됩니다.
- 로컬에서 검사 돌리기:
  ```bash
  python scripts/check_skills.py
  ```
- 스킬 eval을 돌리는 방법과 결과는 `scripts/skill-evals/README.md`에 있습니다.
