# Verify by Running

코드를 읽는 건 검증이 아니다. 사용자가 닿는 방식 그대로 **실행해서** 확인하고, 본 것을 증거로
남긴다. 이게 에이전트를 믿게 만드는 첫 번째 도구다.
(근거: `~/.claude/references/agent-trust-lauren-tan.md` 2부)

## 왜 필요한가

- 검증 수단이 없으면 사람이 검증자이자 병목이 된다.
  - 사람이 앱을 띄우고, "안 되네"라고 확인하고, 스크린샷을 복사해 붙인다.
  - 에이전트는 그걸 추측으로 이해한다.
- 실행 없이 원인을 말하면 에이전트는 자신 있게 틀린다: "분명 이것 때문이에요."
  - 도구 호출을 보면, 봐야 할 코드를 읽지도 않은 경우가 많다.
- 검증은 "좋은 코드"가 아니라 "제대로 **동작하는** 코드"를 보장한다.

## 인식 신호

- "고쳤다 / 된다 / 완료"라고 말하려는데, 근거가 diff를 읽은 것뿐이다.
- 버그 제보·스크린샷을 받았고, 원인을 말하려 한다.
- 테스트가 통과했다. 하지만 테스트가 그 버그를 덮는지 모른다.
- 반대로, 실행 경로가 없는 순수 문서·설정 변경이라면 이 스킬은 과하다.

## 절차

### 0. 무엇을 증명할지 정한다

한 문장으로 정한다. 셋 중 하나다.

- "X를 하면 Y가 보인다" (기능)
- "버그 B가 수정 전에는 재현되고 수정 후에는 사라진다" (버그)
- "기존 동작 Z가 그대로다" (회귀 없음)

### 1. 사전 점검 (읽기 전용, 먼저)

아무것도 바꾸기 전에 확인한다.

```bash
python <my-skills>/.claude/skills/verify-by-running/scripts/preflight.py --port <내가 쓸 포트> [--port <사용자 포트>]
```

- 확인하는 것:
  - 포트 사용 여부와 점유 프로세스
  - git 브랜치·HEAD·미커밋 변경
  - 파이썬·노드 버전
- 필요한 버전이나 환경이 틀리면 진행하지 않는다. 틀린 환경에서 얻은 결과는 증거가 아니다.
- 프로젝트에 `FEATURE_MAP.md`가 있으면 `시작 전제조건`과 `조작 관례`부터 읽는다.

### 2. 격리해서 띄운다

- **사용자가 이미 띄운 서버·브라우저 프로필·로그인 세션은 건드리지 않는다.**
  - 재시작도, 종료도, 거기로 요청 보내기도 하지 않는다.
  - 사용자 데이터를 바꿀 수 있다.
- 비어 있는 **자기 포트**와 임시 데이터 경로로 따로 띄운다.
  - 포트를 정했으면 띄우기 **직전에** `preflight.py --port <그 포트>`로 비었는지 확인한다.
  - 사용 중이면 다른 포트를 고른다. 이미 떠 있는 서버 위에 겹쳐 띄우지 않는다.
- 어떤 인스턴스가 대상인지 모호하면 추측해서 붙지 않는다. 멈추고 묻는다.
- 받은 저장소·폴더 안의 코드만 쓴다. 다른 곳에서 비슷한 파일을 찾아 가져오거나 거기서 띄우지 않는다.
- 띄울 때마다 PID를 기록해 둔다. 5단계에서 **기록한 PID만** 종료한다.
  - 이름으로 한꺼번에 죽이는 명령은 쓰지 않는다: `taskkill /IM python.exe`, `pkill python`, `Stop-Process -Name`.
  - 이런 명령은 사용자의 다른 프로그램까지 모두 죽인다.

### 3. 버그라면: 지금 코드에서 재현부터

- 고치기 **전에** 제보된 조작을 그대로 실행해서 증상을 본다.
- **재현이 안 되면 코드를 고치지 않는다.** 이미 고쳐졌을 수 있다.
  - `git log -p -- <관련 파일>`로 최근 수정을 찾는다.
  - 이전 커밋을 별도 worktree에서 띄워 재현을 확인한다.
    ```bash
    git worktree add <임시경로> <이전커밋>
    ```
    - 작업 트리를 `checkout`으로 바꾸지 않는다. 사용자의 미커밋 변경을 건드리게 된다.
  - 이전 커밋을 **실제로 띄워서** 같은 요청을 보낸다.
    - `git log`나 diff를 읽고 "이전엔 터졌을 것"이라고 하는 건 추론이지 재현이 아니다.
  - 이전 커밋에서 재현되고 지금은 사라졌다면, "이미 고쳐짐 — 배포만 필요할 수 있음"으로 보고한다.
- 재현되면 원인을 **코드를 읽고 실행해서** 좁힌다. 추측으로 단정하지 않는다.

### 4. 고친 뒤: 같은 조작으로 다시 확인한다

- 3단계에서 재현한 조작을 똑같이 다시 해서 증상이 사라졌는지 본다.
- 정상 경로도 한 번 돌려서 회귀가 없는지 본다.
- 끝났다고 판단할 때는 고정 `sleep`이 아니라 **관찰 가능한 끝 상태**를 기다린다: 응답, 문구, 상태 값.
- 콘솔·서버 로그에 새 에러가 없는지 본다.
- 발견한 재현 케이스는 테스트로 고정한다. 기존 테스트가 이 버그를 못 잡았다면 그것도 보고한다.

### 5. 정리한다

- 기록해 둔 PID를 하나씩 종료한다.
  - 재시작하느라 여러 번 띄웠다면 그 PID도 전부 종료한다.
  - 그다음 사용한 포트마다 `preflight.py --port <포트>`로 비었는지 확인한다. 비어 있지 않으면 끝난 게 아니다.
- 임시 worktree(`git worktree remove`)와 임시 파일을 지운다.
- 사용자 인스턴스가 처음 상태 그대로인지 확인한다.

### 6. 증거 형식으로 보고한다

```markdown
- 대상: <증명한 문장>
- 사전 점검: <통과 / 다른 점>
- 한 것: <명령·조작 순서>
- 관찰: <본 것 그대로 — 응답, 문구, 로그 한 줄>
- 수정 전 재현: <재현됨 / 재현 안 됨 / 해당 없음>   (버그일 때)
- 수정 후: <사라짐 / 여전함>                        (버그일 때)
- 증거 파일: <로그·스크린샷 경로 또는 "없음">
- 건너뜀: <못 한 변형과 이유 또는 "없음">
```

- "관찰"에는 **본 것만** 적는다. 코드에서 추론한 것은 "추론:"으로 따로 적는다.
- 못 한 것을 조용히 빼면 보고 전체를 믿을 수 없게 된다. 반드시 "건너뜀"에 적는다.

## 실행 수단 (표면별)

| 표면 | 수단 |
|---|---|
| HTTP API | curl로 실제 요청. 비ASCII 본문은 파일 경유([[non-ascii-via-file]]) |
| 웹 화면 | 브라우저 창으로 열고 요소 읽기, 콘솔 에러 확인. 좌표 클릭보다 선택자·단축키. 페이지 JS 실행은 **읽기 전용** |
| CLI·라이브러리 | 실제 입력으로 실행하고 출력 대조([[real-world-review-cycle]]) |
| 데스크톱 GUI | 자동화 수단이 없으면 "수동 확인 필요"로 건너뜀에 적는다 |
| 성능 | 프로파일러·트레이스를 실제로 떠서 숫자로 말한다. 스크린샷만 보고 원인을 단정하지 않는다 |

## 하지 않는 것

- diff나 스크린샷만 보고 "고쳤다", "원인은 이것"이라고 말하지 않는다.
- 재현하지 않은 버그를 고치지 않는다.
- 사용자 서버를 재시작·종료하지 않는다. 사용자 브라우저 프로필·세션을 쓰지 않는다.
- 추론을 관찰처럼 쓰지 않는다.
