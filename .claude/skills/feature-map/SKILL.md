# Feature Map

UI가 있는 프로젝트에 `FEATURE_MAP.md`를 둔다. 에이전트는 이 파일을 보고 앱을 띄우고,
각 기능까지 **스스로** 찾아가서 동작을 증명한다.

## 왜 필요한가

앱을 띄울 수 있게 해 줘도 에이전트는 헤맨다. "왼쪽 사이드바가 느리다" 같은 보고를 받으면
그 기능이 코드 어디에 있는지, 화면에서 어떻게 가는지 모르기 때문이다. 그동안 사람이 경로를
알려 주는 병목이 되고, 에이전트는 추측으로 엉뚱한 파일을 고친다.

기능별로 "가는 길"을 적어 두면 모호한 보고나 스크린샷만으로도 재현 절차에 바로 닿는다.
이 파일이 곧 **검증의 기준 자료**다. 변경이 동작하는지, 아무것도 깨지지 않았는지 증명할 때
이 파일을 따른다. (근거: Lauren Tan의 Glass 피처 맵. `~/.claude/references/agent-trust-lauren-tan.md` 3부)

## 제일 중요한 원칙: 쓰는 법을 적고, 만든 법은 적지 않는다

- 맵은 **사용자 관점**으로 적는다: 무엇인지, 어떻게 가는지, 어떻게 쓰는지, 도구로 어떻게 조작하는지.
- 내부 구현은 적지 않는다: 함수 동작 원리, 데이터 값, 분기 조건, 목업 데이터 내용 같은 것.
  - 내부는 어떤 문서보다 빨리 바뀐다.
  - 내부가 궁금하면 `파일` 줄의 경로를 따라가 코드를 읽는다.
- 이유: 7개 프로젝트에 맵을 만들었을 때 표본의 약 30%가 부분 오류였다. 그 대부분이 문장으로
  적은 내부 사실이었다. 이 오류는 체커로 잡을 수 없고, 코드가 바뀌면 다시 틀린다.

## 인식 신호

- UI가 있는 프로젝트인데 `FEATURE_MAP.md`가 없다.
- 에이전트가 UI 버그를 받고 코드를 읽지 않은 채 원인을 단정하거나, 화면을 무작정 클릭한다.
- 화면·라우트·버튼·단축키를 추가하거나 이름을 바꿨다. 이때는 맵도 갱신하고 체커를 돌린다.
- UI가 없는 라이브러리·CLI 전용 프로젝트는 대상이 아니다. README의 명령 목록이면 충분하다.

## 파일 구성

- 작은 앱: `FEATURE_MAP.md` 한 파일에 아래 섹션을 모두 둔다.
- 기능이 많은 앱: `FEATURE_MAP.md`는 색인과 공통 섹션만 둔다.
  - 기능마다 파일 하나: `feature-map/<기능>.md`
  - 여러 기능을 가로지르는 여정: `feature-map/cross-cutting-flows.md`
  - 조작하거나 재현하기 전에 해당 기능 파일을 읽는다.

`FEATURE_MAP.md`에 반드시 있어야 하는 섹션 (체커가 확인한다):

1. `## 실행 방법`
   - 명령, 포트·URL, 환경변수(**이름만**, 값은 적지 않는다), 테스트 데이터 위치
2. `## 시작 전제조건`
   - 기능 파일이 따로 정하지 않으면 모든 검증이 가정하는 상태를 적는다.
   - 예: 서버가 떠 있고 건강 확인이 통과함, 로그인 상태, 열린 모달 없음, 기본 설정
   - 도구가 닿을 수 없는 경로(실제 OAuth, OS 권한, 실기기)도 여기에 적는다.
3. `## 조작 관례`
   - 이 앱을 도구로 조작하는 규칙. 아래 "기본 조작 관례"에서 해당하는 것을 고르고 앱에 맞게 쓴다.
4. `## 증거와 건너뜀 보고`
   - 검증 결과를 보고하는 형식. 아래 "증거 보고 형식"을 쓴다.
5. `## 기능`
   - 기능마다 `###` 섹션 하나

## 기능 섹션 형식

체커가 라벨을 읽으므로 라벨은 그대로 쓴다.

```markdown
### <기능 이름>
- 사용자 경로: 첫 화면 → "업로드" 버튼 → 결과 탭
- 단축키: Ctrl+O              (없으면 이 줄 생략)
- 선택자: `[aria-label="업로드"]`, `결과`
- 파일: `static/index.html`, `app/routes/upload.py::upload`
- 검증: 샘플 `examples/a.srt` 업로드 → 결과 탭에 행이 표시되고 콘솔 에러 없음
```

- `선택자`에는 **실행 중인 화면에서 찾을 수 있는 것만** 백틱으로 적는다.
  - 우선순위: ARIA 라벨·`data-*` 속성 → `id` → 보이는 문구 → class (class는 최후 수단).
  - 데스크톱 앱이면 위젯 `objectName`, 접근성 이름, 보이는 버튼·메뉴 문구를 쓴다.
  - 보이는 문구는 코드의 문자열을 공백까지 그대로 복사한다. `"▶ ‖"`를 `"▶‖"`로 줄이면 못 찾는다.
  - 여러 화면이 같이 쓰는 class라면 이 기능에만 있는 표식을 함께 적는다.
- 컴포넌트 이름·함수 이름 같은 **코드 식별자는 선택자가 아니다.** 소스에는 있지만 화면에는 없다.
  - 식별자는 `파일` 줄에 `path::Symbol`로 적는다.
- `파일`에는 저장소 루트 기준 경로를 적는다.
  - **줄 번호는 적지 않는다.** 코드가 조금만 바뀌어도 틀린다. 위치는 `path::함수명`으로 가리킨다.
- `사용자 경로`에 "~에서 링크로 진입"이라고 적었다면 그 링크가 템플릿에 실제로 있는지 확인한다.
  - 없으면 "URL 직접 입력"이라고 적는다.
- `검증`에는 에이전트가 **관찰할 끝 상태**를 적는다: 보이는 문구, 버튼 활성화, 상태 라벨, 응답 코드.
  - 구현 설명("이 함수가 X를 호출한다")은 검증이 아니다.

## 기본 조작 관례

앱에 해당하는 것만 골라 `## 조작 관례`에 적는다.

- **격리**: 사용자가 이미 띄운 서버·브라우저 프로필·로그인 세션에 붙지 않는다.
  - 자기 포트와 자기 프로필로 따로 띄운다. 띄우기 전에 포트가 비어 있는지 확인한다.
  - 대상이 모호하면 추측해서 붙지 말고 멈춘 뒤 묻는다.
  - 끝나면 띄운 프로세스와 탭을 정리한다.
- **사전 점검**: 조작하기 전에 건강 확인부터 한다 (서버 응답, 빌드 신선도, 필요한 버전).
  - 틀린 환경이면 진행하지 않고 멈춘다.
- **대기**: 고정 시간 `sleep`으로 끝났다고 보지 않는다. 관찰 가능한 끝 상태(문구, 버튼 활성화, 상태 라벨)를 폴링한다.
  - 폴링에는 상한 시간을 두고, 넘으면 멈추고 "건너뜀"으로 보고한다.
    - 끝 상태가 영영 안 오는 경우가 있다: 응답 없는 권한 창, 조용히 삼킨 `fetch` 실패, 대상 요소가 없는 페이지.
  - 사건마다 끝 상태를 따로 적는다. 여러 사건을 "X·Y·Z 중 하나가 바뀔 때까지"로 묶지 않는다.
    - 어떤 사건은 그 라벨을 하나도 바꾸지 않는다. 어떤 사건은 라벨을 즉시 바꾸고 실제 전환은 나중에 한다.
- **입력**: 좌표 클릭보다 선택자와 등록된 단축키를 쓴다.
- **읽기 전용 평가**: 페이지에서 JS를 실행할 때는 상태를 **읽는 데만** 쓴다. 앱 동작을 JS로 대신 호출하지 않는다.
- **콘솔**: 기대 결과에 "에러 없음"이 들어 있으면 콘솔을 켜 둔 채 실행한다.
- **건드리지 않기**: 관련 없는 설정·플래그·데이터는 바꾸지 않는다.
  - 테스트로 남긴 기록(예: localStorage)은 보고에 적는다.
- **수동 영역**: OS 파일 드롭, 네이티브 메뉴, 외부 브라우저, 실제 OAuth, 실기기 센서는 도구가 지원하지 않으면 **수동**으로 표시한다.

## 증거 보고 형식

검증을 보고할 때 이 형식을 쓴다. `## 증거와 건너뜀 보고`에 그대로 옮겨 적는다.

```markdown
- 대상: <기능 / 변경>
- 전제조건: 시작 전제조건 충족 여부 (다르면 무엇이 달랐는지)
- 한 것: <실행한 명령·조작 순서>
- 관찰: <본 것을 그대로 — 문구, 개수, 응답 코드, 로그 한 줄>
- 버그 수정이면: 수정 전 커밋에서 재현됨 / 수정 후 사라짐
- 증거 파일: <스크린샷·녹화·로그 경로> (없으면 "없음")
- 건너뜀: <맵에 있는 변형 중 못 한 것과 이유> (없으면 "없음")
```

- 맵에 나열된 변형(메뉴 경로, 단축키 경로, 로컬·원격 등) 가운데 하나라도 빠졌으면 증거는 **불완전**하다.
  - 빠진 것을 "건너뜀"에 적는다. 건너뛴 것을 조용히 빼면, 보고를 믿을 수 없게 된다.
- "관찰"에는 **본 것만** 적는다. 코드에서 추론한 것은 "추론:"으로 따로 적는다.
  - 1차 작성 때 "실행해서 확인했다"는 문장 가운데 코드 분기와 맞지 않는 것이 나왔다.
  - 추론을 관찰처럼 쓰면, 다음 에이전트는 가장 믿을 만해 보이는 문장에서 속는다.

## 절차

1. 코드에서 기능을 전수 수집한다: 라우트, 템플릿, 버튼·메뉴 핸들러, 단축키 바인딩. 기억이나 README만 믿지 않는다.
2. 필수 섹션과 기능 섹션을 쓴다. 내부 구현은 쓰지 않는다.
3. 이 단계에서는 `검증` 문장에 확인 표시를 붙이지 않는다. 실행 확인은 코드 대조가 끝난 뒤 6번에서 한다.
   - 코드를 읽고 쓴 문장은 아직 추론이다. 대조 전에 띄우면 곧 고칠 문장을 조작하게 된다.
4. 체커를 돌린다. 실패하면 **맵을** 코드에 맞게 고친다. 맵에 맞춰 코드를 고치지 않는다.
   ```bash
   python <my-skills>/.claude/skills/feature-map/scripts/check_feature_map.py <프로젝트 루트>
   ```
5. 작성자가 아닌 에이전트에게 무작위 3건 이상을 코드와 대조하게 한다.
   - 체커는 "문자열이 있는가"만 본다. "그 문자열이 정말 이 기능의 것인가"는 못 본다.
   - 검토 기록 (7개 프로젝트, 작성자와 다른 에이전트가 무작위 표본을 코드와 대조):
     - 1차 작성 후 기능 21건 중 7건(33%)이 부분 오류.
     - 체커를 강화하고 전체를 감사한 뒤 21건 중 6건(29%).
     - 이 스킬의 규칙(사용자 관점만, 필수 섹션, 조작 관례)으로 다시 쓴 뒤 기능 21건 중 4건(19%),
       공통 섹션 7건 중 2건.
   - 남은 오류는 시간이 걸리는 동작의 끝 상태를 잘못 적은 것("누르면 카드가 사라진다" 대신 실제로는
     서버 응답 뒤에야 사라짐)과, 그 오류에서 나온 조작 관례의 대기 규칙이 특정 상태에서 끝나지 않는 것이었다.
     "곧바로"인지 "응답 뒤에"인지를 코드에서 확인하고 적는다.
   - 표본 검토만으로는 오류를 놓친다. 표본 3건이 정확했던 맵에서 전수 감사 때 7건이 더 나왔다.
     - 큰 수정 뒤에는 모든 문장을 코드와 대조하는 전수 감사를 한다.
     - 감사 결과는 그대로 적용하지 않는다. 지적마다 코드를 다시 읽고 확인된 것만 고친다.
   - 전수 감사 기록 (7개 프로젝트, sonnet이 모든 문장을 코드와 대조):
     - 문장 847개 중 89개(10.5%)가 틀림·부분 오류. 가장 큰 맵(기능 34개)에서만 64개가 나왔다.
     - 다른 에이전트(opus)가 다시 확인했을 때 지적 59건 중 1건은 기각됐다(`uvicorn[standard]`가 PyYAML을 설치함).
     - 전수 감사를 반영한 뒤 opus가 새 표본을 검토: 기능 21건 중 6건(29%), 공통 섹션 7건 중 3건이 부분 오류.
       - 오류 10건 중 8건은 감사 때 "맞음"으로 넘어간 문장이었다. 2건은 감사 때 고친 문장이었는데 고친 뒤에도 조건이 빠져 있었다.
       - 비율이 줄지 않은 이유는 확인하지 못했다. 가설: opus 검토자가 sonnet 감사자보다 조건을 더 깊이 따진다.
   - 전수 감사에서 새로 나온 오류 유형:
     - 조건부 화면: 버튼·체크칸이 특정 상태에서만 있다.
     - 실패 경로 문구: 성공 문구만 적고 실패 문구를 빠뜨렸다.
     - 표시 형식: 1분이 넘으면 `N초 경과`가 `N분 M초 경과`로 바뀐다.
     - 덮어쓰는 문구: 상태줄 문구가 바로 다음 알림에 덮이거나, 말풍선이 0.4초 만에 바뀐다.
     - `파일` 목록 누락: 같은 기능의 두 번째 동작(삭제·거절)이나 실제로 일을 하는 보조 함수를 빠뜨렸다.
     - 호출처 없는 함수: `파일`에 적은 함수가 정의만 있고 불리지 않는다.
     - 끝나지 않는 대기 규칙: 위 조작 관례의 "대기" 항목을 참고한다.
6. 앱을 실제로 띄워 기능마다 `검증` 문장대로 조작하고, 결과를 맵에 날짜로 표시한다.
   - 코드 대조로는 부족하다. 대조를 두 번 거친 7개 맵에서 실행이 새로 잡은 것:
     - 앱 버그 2개 (버섯을 비출 수 없음, 시작 화면의 `← 뒤로`가 덮개에 가려 안 눌림)
     - 끝나지 않는 대기 규칙 (두 번째 작업부터 앞 작업의 `완료!`가 남아 폴링이 바로 끝남)
     - 조건부 문구, "링크"로 적힌 버튼, 해시보다 늦게 바뀌는 표시
   - 띄우기: `verify-by-running` 스킬의 사전 점검(`preflight.py --port <포트>`)으로 비어 있는 자기 포트를 확인한 뒤 띄운다.
     - 사용자가 띄운 서버·브라우저 프로필에 붙지 않는다. 끝나면 띄운 PID만 멈추고 포트가 비었는지 다시 확인한다.
     - 외부 API·DB에 쓰는 앱은 해당 환경변수를 비우거나 목업 모드로 띄운다. 과금되는 동작은 사용자 승인 뒤에만 누른다.
   - 조작: 맵의 `사용자 경로`·`선택자`·`검증`만 보고 조작한다. 맵에 없는 길로 돌아가면 맵의 결함을 놓친다.
     - 캔버스·애니메이션 앱은 브라우저 창이 화면에 보여야 한다. 숨겨지면 `requestAnimationFrame`이 멈춰 화면이 갱신되지 않는다.
     - 파일 선택 창·내려받기·공유·클립보드는 사용자 환경에 흔적을 남기므로 누르기 전에 묻는다.
       - 파일 입력은 저장소 예시 파일을 `DataTransfer`로 `input.files`에 넣어 대신할 수 있다.
   - 표시: 한 형식만 쓴다.
     - 확인한 문장 끝에 `(YYYY-MM-DD 실행 확인)`을 붙인다. 조건을 좁혔으면 괄호 안에 쓴다: `(2026-09-27 실행 확인, 목업 모드)`.
     - 못 한 것은 `(미확인, 이유)`로 쓴다: `(미확인, 실기기 카메라 필요)`. 이유가 이미 문장에 있으면 `(미확인)`만 쓴다.
     - 본 것을 따로 남길 때는 `검증` 아래 줄에 쓴다: `- 실행 관찰: <본 것> (2026-09-27 실행 확인)`.
     - 콜론(`(미확인: …)`)이나 앞에 붙인 조건(`(표시 부분만 2026-09-27 실행 확인)`) 같은 다른 형식은 쓰지 않는다. 한 형식이어야 `grep`으로 셀 수 있다.
     - 맵 맨 위 믿는 범위(7번)에 실행 날짜, 포트, 모드, 확인한 기능 수를 한 줄로 적는다.
   - 문장과 다르게 동작하면:
     - 맵이 틀렸으면 맵을 고치고 표시를 붙인다.
     - 앱이 틀렸으면(버그) 맵을 앱에 맞추지 않는다. 재현 절차를 증거 보고 형식으로 사용자에게 알리고, 코드 수정은 맵 커밋과 따로 한다.
   - 남긴 흔적(localStorage, 테스트 기록, 권한 요청)은 보고에 적는다.
7. 맵 맨 위에 믿는 범위를 적는다: 체커가 보장하는 것(파일·선택자·섹션)과 보장하지 못하는 것(문장).
   - 이 틀을 쓴다. 날짜·포트·기능 수는 맵이 바뀔 때마다 고친다.
     ```markdown
     > **이 맵을 믿는 범위 (코드 대조 YYYY-MM-DD, 실행 확인 YYYY-MM-DD)**
     > - 체커(`check_feature_map.py`)는 `파일`·`선택자`·필수 섹션만 코드와 대조한다. `사용자 경로`·`검증` 문장은 못 본다.
     > - 코드 대조: <날짜와 방식. 예: 2026-09-27 전수 감사 반영>
     > - 실행 확인: <날짜>, 포트 <N>, <모드·조건>, 기능 <전체>개 중 <확인>개. 확인한 문장에 `(날짜 실행 확인)`, 못 한 것에 `(미확인, 이유)`를 붙였다.
     >   - 누르지 않은 것과 이유, 남은 흔적
     > - 표시가 없는 문장은 실행으로 확인되지 않았다.
     > - 문장대로 동작하지 않으면 버그로 단정하기 전에 `파일` 줄의 코드부터 읽는다.
     > - <이 프로젝트만의 주의>
     ```
   - 기능 수는 기억으로 적지 않는다. `## 기능` 아래 `###` 가운데 실행 확인 표시가 있는 것을 센다.
   - 실행하지 않았으면 제목에서 `실행 확인` 부분을 빼고, 실행 확인 줄에는 `없음`이라고 쓴다.
   - "이번에는 앱을 띄우지 않았다" 같은 옛 문장은 실행한 뒤 지운다. 남기면 바로 아래 실행 기록과 모순된다.

## 하지 않는 것

- 시크릿·API 키 값·개인정보를 맵에 적지 않는다 (환경변수 이름만).
- 맵을 만들면서 앱 코드를 고치지 않는다. 맵 작업은 문서 작업이다.
- 체커를 통과시키려고 선택자를 느슨하게(예: `div`) 적지 않는다.
- 공개 저장소라면 숨긴 페이지·관리자 경로가 맵으로 드러나지 않게 한다. 커밋하지 않거나 ignore한다.
